# Choosing evidence for a user outcome

These fictional examples help select a check; they do not establish current product behaviour.

## AI pipeline

Outcome: after an authorised extraction, the operator sees its evaluation and knows what needs attention.

Check the actual automatic trigger with a controlled input. Follow its identity through persisted evaluation and the operator's view. Retain the run/version, evaluation result and readback. Exercise a controlled evaluation failure and observe the documented retry or intervention path. A manually uploaded score proves only that upload. A citation check may show a source exists while leaving meaning unassessed; label that gap explicitly.

Acceptance may remain blocked if credentials or live access are unavailable. Keep successful local checks but do not rename them end-to-end proof. Use an existing approved test environment and budget; this example authorises no calls.

## Website

Outcome: a visitor can understand an offer and complete its intended next step on mobile.

A build proves the source compiles. A rendered walkthrough at the relevant viewport, with the action and resulting state observed, tests the outcome. Record the revision, environment and screenshot or trace. Do not send a real enquiry just to test the interface unless that action is authorised; use the approved test route or report the remaining gap.

## Resume

If tests passed but remote readback failed, retain both facts. Resume at the missing readback using the same owning work record. Do not regenerate the feature plan, rerun paid generation without authority or describe the feature as fully verified.
